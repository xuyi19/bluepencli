## 二、分发与导入：文档要求 vs 实际（第六、七部分细对）

这一节是本文档最"细"的部分，也是差距最集中的地方。

### 2.1 导入过程（文档 6.2 / 6.3）

| 文档要求 | 实际 |
|---|---|
| 导入时**逐条回显验证步骤**（`✓ Magic Number 校验通过` / `✓ 签名验证通过` / `✓ 水印校验通过（用户：xxx）` / `正在解密…` / `正在入库…`） | ❌ 只有**结束后一条** toast：`已导入 N 套 / M 道题（水印：xxx）`。<br>中间过程的校验错误会分别提示（口令错可重试、签名/格式错直接说清）——**但成功路径看不到过程** |
| 导入结果汇总（题目数 / 已校准数 / 待校准数 / 年份范围 / 题型分布） | 🟡 有"套数 / 题数 / 水印"，**没有"已校准 / 待校准"统计**（因为校准覆盖率本身就是空白） |
| 批量导入（一次拖入多个 .bpq，汇总确认 `[全部导入] [逐个选择]`） | ❌ 只取第一个文件（`e.target.files?.[0]`） |
| 错误处理六种（签名无效 / 水印不匹配 / 设备不匹配 / 已过期 / 版本过旧 / 重复导入） | 🟡 有签名 / 口令 / 格式三类；**水印不匹配、设备不匹配、已过期、版本过旧、重复导入覆盖确认都没有**（因为授权与设备绑定未实现） |

### 2.2 导入后管理（文档 6.5）

文档要一个「我的题库」页面：内置题库 / 私有题库（含导入时间、题目数、水印、[查看] [删除]）/ 用户导入题库，
操作含查看详情、删除（带确认）、更新（新版覆盖）、导出统计（不导出内容）。

**实际：❌ 整个页面不存在。** 导入的题直接进 `questions` 表混在题库里，无法按来源分组查看、
无法删除已导入的包、无法看"这个包是谁的水印"。**这是分发体系里最明显的体验缺口**——
用户导入后没有任何"我导入过什么"的凭据。

### 2.3 授权与激活（第七部分）

| 模式 | 文档 | 实际 |
|---|---|---|
| A 无授权 | 拿到即可导入 | ✅ **这是目前唯一生效的模式** |
| B 水印校验 | 首次输入邮箱 → `sha256(email+salt)` 生成本地标识 → 导入时校验包水印与本地标识匹配 | ❌ 水印字段**存在且能读出**（导入时显示在提示里），但**不做匹配校验**，纯展示 |
| C 授权码 | `BP-XXXX-XXXX-XXXX-XXXX`，HMAC 校验 + 与包水印匹配 + 写激活记录 | ❌ 未做 |
| 激活记录 | IndexedDB `activations` 表（bpqId / userFingerprint / deviceFingerprint / activatedAt / expiresAt / authCodeHash） | ❌ 表都没建 |
| 设备绑定 | 设备指纹写入 IndexedDB，启动时校验，不匹配拒绝加载 | ❌ 未做 |
| 安全强度分级（L1–L4） | 按需选择强度 | ❌ 未做 |

> **判断**：文档第七部分是"可选增强"，实际没做**目前不算问题**——
> 模式 A 的思路是"信任 + 溯源"，对"发给同学内测"这个阶段是合适的。
> 但**模式 B 的成本极低**（一个邮箱输入框 + 一次哈希比对），却能挡住"随手转发给群里"，
> 性价比很高，值得做。

### 2.4 存储与三层题库（第九、十部分）

| 文档要求 | 实际 |
|---|---|
| IndexedDB 新增 `BPQRecord` / `Activation` / `LocalIdentity` 三张表 | ❌ 现有 5 张表（articles / questions / records / notes / mistakes），**一张新表都没加** |
| 题库列表区分「内置 / 私有 / 用户导入」三类 | 🟡 能区分**公开 / 私有**（按 `tier`），**没有"用户导入"这一层** |
| 题库优先级：用户层 > 私有层 > 内置层，按 `questionId` 去重覆盖 | ❌ 无优先级与去重逻辑 |
| 用户层流程：下载 PDF → OCR → Markdown → 导入工具 → 预解析 → 校准 → 入库 | ❌ 未做（作者侧有 PDF 直出结构化 JSON 的管线，但不是给用户的） |

## 六、结论

**这份文档的"硬核三件套"（加密、签名、水印）不仅做完，还多了两层**：口令批次化（换批必换口令，
复用会被拒）和发放台账（记 sha256，可事后核对"流转的是不是我发的那份"）。
作者侧打包从"一个工具"变成"三段式 + 按人改水印 + 批量"，比文档设想更细。

**但文档真正想解决的那个体验闭环没闭上**：文档反复强调"用户一键导入、看得见过程、导入后可管理"，
而实际是"拖进去 → 一条 toast → 题混进题库，无法查看来源、无法删除、无法知道包的版本"。
再加"用户层题库"完全没做——**这套分发体系目前只完成了"作者能发"，没完成"用户能管"**。

**最该补的三件事**（都是小改动、高回报）：
1. 导入过程逐条回显 + 导入后给我一个「我的题库」页（看得见、删得掉）
2. 记录里存下"标准版本 / prompt 版本 / 模型 / 合议方式"（让分数的来源可追溯）
3. 可信度加"题库来源"维度（私有校准 / 用户校准 / 无标准三档）

这三件加起来估计一两个晚上，但它们把"可校准、可复算、可解释"从**口号**变成**界面上看得见的东西**
——而那正是这个项目对外讲的核心差异化。
