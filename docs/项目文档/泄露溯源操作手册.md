# 蓝笔申论 · 泄露溯源操作手册

> 版本：2026-10-08 ｜ 适用：v2 加密题库包（BPQ00002）与 v1 明文包（BPQ00001）
> 配套机制：`.bpq` 加密 + 签名（`frontend/src/bpq/`）、发放工具（`.tools/exams/issue.mjs`）、
> 发放台账（`私有题库/发放台账.json`）
> 定位：方案优化第二版 §8「泄露溯源」的配套操作文档——发现泄露时**照着做**，不靠回忆。

---

## 〇、为什么能溯源（四条防线，一分钟版）

| # | 机制 | 溯源时起什么作用 |
|---|---|---|
| 1 | **逐人水印** | 每份包的 `userFingerprint` 都写着收件人，一人一包一份水印 |
| 2 | **水印在外层明文** | 封包时故意把「这是谁的包」留在**不解密就能看到**的外层——拿到文件就能读出水印，不需要口令 |
| 3 | **签名覆盖水印** | ECDSA 签名覆盖**除签名外的一切字段（含水印与密文）**。改水印、抹水印、换一个字节，验签都失败——「被动过手脚」反过来成了证据 |
| 4 | **台账记 sha256** | 每份发放出去的文件都记了哈希。哈希一致 = 流转的**就是**发给某个人的那份原件，文件名被改也赖不掉 |

> 口令与包**分开两条路**（包走 A 渠道、口令当面/另发），所以只拿到包不解密不了正文；
> 反过来，泄露者把口令也发出去了的情况，见 **场景 B**。

## 一、场景 A：拿到泄露的 .bpq 文件本身（最常见，也最好办）

### 第 0 步：保住证据

**先复制一份只读备份**，之后所有操作都在备份上做，别动原文件：

```powershell
Copy-Item "收到的泄露样本.bpq" "$env:USERPROFILE\Desktop\leak-sample.bpq"
```

### 第 1 步：算文件哈希（跟台账比对用）

```powershell
Get-FileHash "leak-sample.bpq" -Algorithm SHA256
# 或 bash：sha256sum leak-sample.bpq
```

记下这个值。它是「流转的是不是原件」的判据。

### 第 2 步：读水印（不需要口令）

水印在外层明文，一行 node 就能读出来（在仓库根目录跑）：

```bash
node -e "const p=JSON.parse(require('fs').readFileSync('leak-sample.bpq','utf8')); console.log(JSON.stringify({magic:p.magic,version:p.version,issuer:p.issuer,issuedAt:p.issuedAt,userFingerprint:p.userFingerprint,sig:p.sig?.keyId||'(v1无签名)'},null,1))"
```

期望输出（示例）：

```json
{
 "magic": "BPQ00002",
 "version": 2,
 "issuer": "许一 <xuconghui_03@qq.com>",
 "issuedAt": "2026-09-30T21:14:03+08:00",
 "userFingerprint": "张三/zhangsan@example.com",
 "sig": "bpq-2026a1b2"
}
```

`userFingerprint` 就是发放时 `--user` 传入的收件人标识 → **直接定位到人**。
`sig.keyId` 是签发用的公钥编号，`issuedAt` 是签发时间，都可以跟台账交叉核对。

也可以用现成校验脚本（会顺带验签、报卷数题数）：

```bash
node .tools/verify-bpq.mjs leak-sample.bpq            # 只验签名，不需要口令
node .tools/verify-bpq.mjs leak-sample.bpq --passphrase "口令"   # 连正文一起验
```

### 第 3 步：验签——判断文件有没有被动过

`verify-bpq.mjs` 不带口令时输出里的「签名：✓ / ✗」就是判据：

- **✓ 签名通过** → 这份包从签发到现在一个字节都没变，水印可信。
- **✗ 签名失败** → 有人改过外层字段（最典型：想抹掉或替换水印）。
  **注意：这不能抹掉溯源结论**——见第 4 步，sha256 会把原件认出来。

### 第 4 步：跟台账比对（定人 + 定原件）

台账在 `私有题库/发放台账.json`（人读版 `.md`），每条记录含
`user / batch / file / sha256 / keyId / at`：

```bash
# 打印台账
node .tools/exams/issue.mjs --ledger

# 核对台账与磁盘上现存文件（被改过的包会在这里现形）
node .tools/exams/issue.mjs --verify-ledger
```

比对逻辑：

| 比对项 | 结果 | 结论 |
|---|---|---|
| 水印 ↔ `records[].user` | 有这个人 | **溯源完成**：泄露的是发给这个人的包 |
| 文件 sha256 ↔ `records[].sha256` | 一致 | 且流转的是**原件**，没改过 |
| 文件 sha256 ↔ 台账 | 全都不一致 | 包被改过（配合签名失败双重坐实），但水印若仍可读、签名若仍通过，水印结论不变 |
| 水印在台账里查无此人 | — | 伪造包或测试包：验签会失败（签名私钥只有作者有），威胁有限 |

### 场景 A 结论模板

> 泄露样本 `xxx.bpq`（sha256 `ab12…`）水印为「张三/zhangsan@example.com」，
> 签名验证通过，与 2026-09-30 发放台账记录一致。
> → 认定为发给张三的原始包被二次传播，且传播的是未修改原件。

## 二、场景 B：泄露的是内容（截图 / 复制的文字），拿不到文件

水印跟着**文件**走，拿不到文件就读不出水印。此时目标是**圈定泄露范围**，按批次处置：

1. **从内容认卷子**：正文里找年份、卷名特征（如「2023年国家公务员考试《申论》」），
   确定泄的是哪几卷 → 都 ≥2022，全部出自私有题库包。
2. **口令是唯一钥匙**：能打开这几卷内容的，只有持有某一批次口令的人。
   私有卷不公开分发，所以**嫌疑范围 = 该批次全部收件人**（台账 `records[].batch` 可列出）。
3. **交叉缩小范围**（能拿到一点文件痕迹时）：截图里若带了导入页的「水印：…」回显
   （导入 UI 会显示 keyId 与水印，见 C1 导入回显），水印一样能读 → 回到场景 A。

**处置按「批次疑似泄露」执行**（见第四节），而不是只针对某一个人。

## 三、场景 C：包验签失败 / 哈希对不上

| 现象 | 含义 | 动作 |
|---|---|---|
| 签名失败 + sha256 与台账一份都一致 | 台账对应的**原件**没变，但手里这份是改过的赝品 | 以台账原件水印为准；赝品说明有人在"去水印"，警惕性升级 |
| 签名失败 + sha256 对不上任何记录 | 手里这份既不是原件也验不过签名——**改过的包** | 按场景 A 第 2 步读水印（外层字段改了不等于读不出）；读不出就按场景 B 圈批次 |
| `--verify-ledger` 报「N 份包哈希对不上」 | **磁盘上的发放包**被改过，或台账被动过 | 先确认台账文件没被编辑（git/备份比对），再逐份重算 sha256 定位 |
| 私钥泄露嫌疑（keyId 正确但能签出新包） | 最严重 | 私钥文件只有 `BPQ_PRIVATE_KEY` 路径那一份；确认权限，必要时换钥重新走 `bpq-keygen.mjs`，全员重发 |

## 四、定位之后：处置动作

1. **换批次口令**（核心动作）：
   ```bash
   node .tools/exams/issue.mjs --new-batch "2026秋-1班-2" --note "1班泄露后换发"
   ```
   新批次口令**随机生成**，显式复用旧口令会被直接拒绝（`--allow-reuse` 才放行，别用）。
   旧批次口令自此不再对任何新发放生效。
2. **逐人重发**：对批次里每个无辜收件人重新 `--user … --batch <新批次>`。
   每份新包**新水印 + 新 IV 重新加密**——同一明文发给两个人，密文也不同。
3. **口令传递仍然分包两条路**，别因为赶时间把口令塞进同一个文件/同一条消息。
4. **不做的**：不在群里公开「谁泄露」；不发"补丁包"；不删台账记录（历史记录是证据）。

## 五、发放前体检清单（预防 > 溯源）

每批发放前过一遍：

- [ ] `node .tools/verify-bpq.mjs <文件> --passphrase "口令"` —— 末行「✓ 可以发出去」
- [ ] 发出去的是**加密包（BPQ00002）**，不是 v1 明文包（`magic` 字段确认）
- [ ] `node .tools/exams/issue.mjs --verify-ledger` —— 台账与磁盘一致
- [ ] 口令与包**分开两条路**给
- [ ] 新批次口令随机生成，没复用旧批次
- [ ] 桌面版/单文件版产物过 `check_release_private.py`（公开渠道不带 ≥2022 卷）

## 六、三十秒演练（伪造数据演示全流程）

```
1. 同事拿到一份来路不明的包 leak.bpq
2. sha256sum leak.bpq                        → 3f9c…
3. node -e "…userFingerprint…"               → "张三/zhangsan@example.com"
4. node .tools/verify-bpq.mjs leak.bpq       → 签名 ✓（未篡改）
5. node .tools/exams/issue.mjs --ledger      → 台账第 3 条：张三 / 2026秋-1班 / sha256 3f9c… 一致
6. 结论：张三的原始包被二次传播 → 找张三核实；该批次口令作废换发
```
