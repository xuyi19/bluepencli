# 蓝笔申论 · 上线部署可行性分析

> 结论先行：**技术上已经具备上线条件**——前端双产物、后端网关、跨域问题都已解决。
> 真正卡住上线的是三个非技术问题：**谁付 API 费用、用户怎么鉴权、成本怎么控**。
> 另外有一个反直觉的结论：**上线会和「单文件发给别人」这个核心优势冲突**，两者需要分开定位。

---

## 一、现状盘点

| 维度 | 现状 | 上线是否需要改 |
|---|---|---|
| 前端 | Vue3 + Vite，双产物（网站版 / 单文件版） | 否，已完成 |
| 后端 | FastAPI 网关（并发调度 + 记账），SQLite 可选 | 否，已完成 |
| 跨域 | 后端代理转发，线上同域部署后 CORS 自动消失 | 否，已完成 |
| 持久化 | SQLite 零配置，`ENABLE_PERSISTENCE` 可一键关闭 | 否，已完成 |
| **鉴权** | **无** | **是，必须补** |
| **计费 / 配额** | **无** | **是，必须补** |
| 部署配置 | 无（本地 uvicorn + vite） | 是 |
| 监控告警 | 无 | 建议补 |

## 二、三种上线形态（按投入从低到高）

### 形态 A：纯静态托管 + 用户自带 Key

把 `frontend/dist/` 丢到 GitHub Pages / Vercel / 对象存储，不部署后端。

- **优点**：零服务器成本、零维护、五分钟上线
- **缺点**：
  - 浏览器直连 LLM 会撞 **CORS**（DeepSeek 官方接口不允许任意来源跨域）
  - 用户的 API Key 存在自己浏览器里（localStorage），泄露风险由用户承担
  - 每个使用者都得自己去申请 Key —— 门槛直接筛掉 90% 的人
- **适用**：作品集演示页，或者面向"有 Key 的技术用户"

> 这条路的本质是"分发工具"，不是"提供产品"。**它和单文件版是同一个定位，没必要重复做。**

### 形态 B：前后端一体部署（推荐，作品集首选）

一台最便宜的云服务器（2C2G 即可），Nginx 托管前端静态文件 + 反代 `/api` 到 FastAPI。

- **优点**：
  - CORS 问题彻底消失（同域）
  - Key 只存在服务端 `.env`，用户零配置，打开就能用
  - 有 `/docs` 交互式 API 文档，演示效果好
- **缺点**：**你在为所有人的调用付费**，必须配套鉴权与限流
- **适用**：毕设答辩现场演示、小范围给同学用

### 形态 C：容器化 + 正式上线

Docker Compose（前端 + 后端 + 反向代理 + 可选 PostgreSQL），后续可平滑上云。

- **优点**：一键部署、环境一致、可水平扩展
- **缺点**：需要处理域名备案、HTTPS 证书、日志采集、备份
- **适用**：真的要当成一个长期运营的产品

## 三、真正的阻塞项（不是技术）

### 1. API 费用由谁承担 —— 最关键

| 方案 | 做法 | 代价 |
|---|---|---|
| **服务端代付** | `.env` 里配你的 Key，用户直接用 | 有人恶意刷就会烧你的钱，**必须配限流** |
| **用户自带** | 设置页填自己的 Key，存 localStorage | 用户门槛高，且纯静态部署会有 CORS |
| **混合** | 默认用服务端额度，用完引导用户填自己的 | 体验最好，实现成本中等 |

> 建议：**内测用服务端代付 + 每 IP 每日限额；公开则切混合模式。**

### 2. 鉴权与滥用防护

当前后端**没有任何鉴权**——任何人知道你服务器地址就能白嫖你的 API 额度。

上线前至少要补其中一项：

- 最简单的：一个共享访问码（`X-Access-Code` 请求头，Nginx 层校验）
- 中等：接入第三方登录（GitHub OAuth），按账号限额
- 完整：邮箱注册 + JWT + 配额表

**限流必做**，且要按「批改次数」限而不是按「请求次数」限——因为一次三师圆桌 = 3~5 次 LLM 调用，按请求限会误伤。

### 3. 成本模型（必须先算清楚）

按 DeepSeek 现价（输入 ¥2 / 百万 token，输出 ¥8 / 百万 token）粗算：

| 模式 | 单次输入 token | 单次输出 token | 估算成本 |
|---|---|---|---|
| 单师批改 | ~1,300 | ~800 | **≈ ¥0.009** |
| 双师联合 | ~2,600 | ~1,600 | ≈ ¥0.018 |
| 三师圆桌（含辩论合议） | ~6,000 | ~3,500 | **≈ ¥0.04** |
| 三师圆桌 + 深度模式 | ~45,000 | ~4,000 | **≈ ¥0.12** |
| 五师圆桌 + 深度模式 | ~85,000 | ~6,000 | **≈ ¥0.22** |

> ⚠️ 深度模式把每位老师的方法论原文（2~3 万字）整篇注入，token 会涨 15~20 倍。
> **如果 100 个用户每天批改 3 次、都用五师深度模式：约 ¥66/天，也就是 ¥2,000/月。**

这就是为什么**必须做限流，并且默认关闭深度模式**。

### 4. 数据与合规

- 用户作答内容（可能含个人信息）——当前只存浏览器本地 IndexedDB，**这是最安全的设计，建议保持**
- 后端只记任务级指标（模式、分数、耗时、token），不记作答正文——已经这么设计了
- 若将来要存用户内容，需要：隐私政策、数据删除通道、传输加密
- 题目与文章素材的版权：内置的 31 篇官媒时评用于个人学习，公开站点建议替换为自采内容

## 四、数据库：当前不做，未来怎么做

### 当前状态

- 后端用 **SQLite 文件**（`backend/data/bluepencil.db`），**不需要安装任何数据库服务**，启动时自动建表
- 想彻底不做数据库：`.env` 里设 `ENABLE_PERSISTENCE=False`，后端立刻退回为纯网关，不建表、不落盘

### 为什么这样设计

用户内容数据（作答、笔记、错题、复习卡片）刻意留在**前端 IndexedDB**，因为：
1. 单文件版必须能独立工作——没有后端也得能存东西
2. 内容不出本地，隐私风险最低
3. 后端职责单一：AI 网关 + 成本记账

### 未来上线要加什么

| 表 | 用途 |
|---|---|
| `users` | 账号、邮箱、创建时间 |
| `quotas` | 每用户 / 每 IP 的日配额与已用量 |
| `grading_tasks` | 已有，扩展 `user_id` 外键 |
| `llm_call_logs` | 已有，用于成本归因 |
| `usage_daily` | 按天聚合，供看板与告警 |

### 迁移路径（工作量很小）

SQLAlchemy 已经把抽象层做好了，迁移只需三步：
1. `.env` 里把 `DB_URL` 换成 `mysql+asyncmy://...` 或 `postgresql+asyncpg://...`
2. 装对应驱动，`requirements.txt` 加一行
3. 引入 Alembic 管理表结构变更（现在靠 `create_all`，上手够用，上线要换）

**结论：数据库这块的架构债是可控的，现在不做不影响将来加。**

## 五、部署清单（形态 B 具体做法）

### 后端（Linux 服务器）

```bash
# 1. 拉代码
git clone <repo> /opt/bluepencil && cd /opt/bluepencil/backend

# 2. 虚拟环境 + 依赖
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 3. 配置
cp .env.example .env
vim .env     # 填 LLM_API_KEY、设 DEBUG=False、CORS_ORIGINS 收窄为你的域名

# 4. 启动（systemd 托管）
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 2
```

### 前端

```bash
cd /opt/bluepencil/frontend
npm ci && npm run build      # 产出 dist/
```

### Nginx

```nginx
server {
    listen 80;
    server_name your-domain.com;
    root /opt/bluepencil/frontend/dist;

    # 前端路由（hash 模式其实不需要，留作兜底）
    location / { try_files $uri $uri/ /index.html; }

    # API 反代 —— 同域之后 CORS 问题自动消失
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;

        # 流式批改必须关缓冲，否则前端看不到实时输出
        proxy_buffering off;
        proxy_read_timeout 300s;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

> `proxy_buffering off` 这条别漏——本项目的批改是 SSE 流式输出，Nginx 默认会攒够一个 buffer 才吐给前端，表现就是"卡半天然后一次性出现"。

### Docker（形态 C 起步版）

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY backend/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY backend/ .
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

前端用 `nginx:alpine` 单独一个镜像托管 `dist/`，两者用 Compose 串起来。

## 六、分阶段路线建议

| 阶段 | 目标 | 要做的事 | 预计工作量 |
|---|---|---|---|
| **P0 本地演示** | 答辩 / 面试能现场跑 | 已完成（本地前后端跑通） | — |
| **P1 小范围内测** | 给 ≤10 个同学用 | 形态 B 部署 + 共享访问码 + 每日限额 20 次 | 1 天 |
| **P2 半公开** | ≤100 人 | GitHub OAuth + 配额表 + 成本看板 + 关闭深度模式默认 | 3~5 天 |
| **P3 正式上线** | 面向公众 | 域名备案 + HTTPS + 监控告警 + 隐私政策 + 内容替换 | 1~2 周 |

### 关于定位的一个提醒

「单文件发给别人双击就用」和「上线成网站」**是两种产品**：

- **单文件版**：无服务器、无账号、用户自带 Key、零边际成本 → 适合分发与作品集附件
- **网站版**：有服务器、有账号、可能你付费、有边际成本 → 适合演示与运营

两者可以共用同一套前端代码（本项目已经做到了），**但运营策略必须分开想**，否则会陷入"既想让人随便用、又不想付钱"的矛盾。

## 七、风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| API 额度被恶意刷 | 直接经济损失 | 限流 + 按批改次数计费 + 余额告警 |
| 五师 + 深度模式成本失控 | 单次 ¥0.22，量大很贵 | 默认关闭深度模式；深度模式做二次确认 |
| 上游模型改价 / 限流 | 服务不可用 | 配置里支持随意换 base_url；做降级提示 |
| 内置文章版权 | 合规风险 | 公开站点换成自采内容或获得授权 |
| 用户作答内容泄露 | 隐私 / 法律风险 | 内容只存本地（已做到），后端不落正文 |
| 长文批改超时 | 体验差 | 已设 180s 超时 + 2 次重试；前端可拆批 |
| SQLite 并发写锁 | 高并发时报错 | 上量前换 PostgreSQL（改一行 DB_URL） |

---

## 八、一句话总结

**技术层面已经没有阻塞项了**——前后端分开、双产物构建、CORS 绕开、数据库可选，这些都已落地。
上线前唯一必须补的是**"谁能用、能用多少"这两道门**：一个访问控制，一个配额限制。
在这两道门装好之前，建议只做 P0/P1，别急着公开——不是因为技术不行，是因为**API 账单会把技术问题变成钱的问题**。
